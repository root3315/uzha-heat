# Как мы работаем с UzHa

Коротко: задача в issue, ветка, маленькие осмысленные коммиты, PR с проверкой, ревью, squash в `main`.
Ниже подробности.

## Подготовка

```bash
git clone https://github.com/root3315/uzha-heat.git
cd uzha-heat

# сайт
cd web && npm ci && npm run dev      # http://localhost:5173

# пайплайн (нужен только если пересчитываете данные)
pip install -r pipeline/requirements.txt
python -m pytest pipeline/tests -q
```

Готовые данные уже лежат в `web/public/data/`, для работы над сайтом пайплайн запускать не нужно.
На Windows перед запуском пайплайна задайте `PYTHONUTF8=1`.

## Где что лежит

| Папка | Что внутри |
|---|---|
| `pipeline/uzha/sources/` | загрузка одного источника: Landsat, Sentinel-2, WorldCover, DEM, OSM, WorldPop |
| `pipeline/uzha/` | сетка, признаки, модель, экспорт |
| `docs/data-contract.md` | формат JSON между пайплайном и сайтом. Это граница между частями |
| `web/src/data/` | загрузка и проверка JSON по контракту |
| `web/src/domain/` | чистая логика: изотермы, разрез, ответы, рекомендации. Без React и MapLibre, всё под тестами |
| `web/src/map/` | MapLibre и слои |
| `web/src/ui/` | компоненты: главная, инструмент, панель |
| `web/src/report/` | отчёт для печати |

Правило: расчёты пишутся в `domain/` как чистые функции с тестом, а компонент только показывает результат.

## Задача и ветка

1. **Issue.** Заголовок говорит, что сделать. В теле: зачем и когда задача считается готовой.
   Опечатку можно поправить без issue, но всё равно через PR.
2. **Ветка от свежего `main`**, с номером issue в имени:
   - `feat/<N>-коротко` — новое
   - `fix/<N>-коротко` — исправление
   - `docs/<N>-...`, `chore/<N>-...`

   В `main` напрямую не коммитим.

## Коммиты

[Conventional Commits](https://www.conventionalcommits.org/ru/) с областью:

```
feat(web): show people in the hottest cells
fix(pipeline): cap each Overpass request at 180 s
chore(data): rebuild Bukhara dataset
docs: describe the TV box deploy
ci: run web build on pull requests
```

- Типы: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `ci`, `perf`, `style`.
- Области: `web`, `pipeline`, `data`. Для `docs` и `ci` область можно не писать.
- Повелительное наклонение, коротко, без точки в конце. Пишем по-английски, как вся история.
- Один коммит — одно логическое изменение. «Поправил всё» не пишем.

## Pull request

В описании:

- **что сделано и зачем**;
- **как проверено**: команды, цифры тестов, скрин для UI (ссылкой на файл в коммите);
- **риски** и что осталось;
- `Closes #N`.

Перед тем как просить ревью: `npm test` и `npm run build` в `web/`, `pytest` для пайплайна.
CI гоняет то же самое на каждом PR. Красный PR не мерджим.

Ревью оставляем комментариями в PR, исправления добавляем новыми коммитами в ту же ветку.
Merge делаем через **Squash and merge**, ветку после этого удаляем.

## Код

**TypeScript**
- `strict`, никакого `any`. Если данные приходят снаружи, их проверяют в `web/src/data/parse.ts`.
- Маленькие функции с понятными именами. Мёртвый и закомментированный код не оставляем.
- Новая логика идёт с тестом в `*.test.ts` рядом с файлом.

**Python**
- Один источник данных — один модуль в `sources/`.
- Сетевые запросы с таймаутом и повтором (смотрите `sources/osm.py`), скачанное кэшируется в `pipeline/cache/`.
- Если меняется формат JSON, сначала правим `docs/data-contract.md`, потом пайплайн и парсер на сайте, всё в одном PR.

**Данные**
- Цифры на сайте берутся только из данных, придуманных чисел нет.
- Эффект мер приводим со ссылкой на исследование.

## Интерфейс и тексты

- Цвет на карте означает только температуру. Причины рисуются штриховкой и иконками.
- Пишем коротко и по делу, как человек: без «инновационный», «умный анализ» и прочего шума.
- Вместо длинного тире ставим точку, запятую или двоеточие.
- У температуры пишем, что это поверхность, а не воздух.
- Проверяем на телефоне (360–414 px) и на ПК: нет горизонтального скролла, кнопки не меньше 44 px.

## Секреты

Ключей и паролей в репозитории быть не должно. Если появятся, то только в `.env`, который в `.gitignore`,
а рядом лежит `.env.example` с заглушками. Перед коммитом посмотрите дифф.
